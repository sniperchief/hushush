# Deploying the backend to Railway (Zcash testnet)

One Railway service runs the hushush backend: **payroll-api** (public, HTTPS)
and the **payout wallet** (private, inside the same container). The database
is Supabase; the web app runs on Vercel and calls payroll-api with
`PAYROLL_API_TOKEN`. Testnet only: the network is compiled in.

```
Vercel (web) ──HTTPS + token──▶ Railway service ┬ payroll-api   0.0.0.0:$PORT  (public)
                                                └ payout-wallet 127.0.0.1:7979 (private)
                                                   └ volume /data: wallet DB, encrypted seed,
                                                     payment-intent store
                                 Supabase Postgres ◀── payroll-api (TLS, CA-verified)
```

## Files

| File | What |
|---|---|
| `deploy/api.Dockerfile` | Builds payroll-api, payout-wallet and the wallet CLI (release, 2 parallel jobs), then a slim Debian runtime with `age` and `tini` |
| `deploy/start.sh` | Prepares the wallet from its secrets, then runs both processes; if either exits, the container exits and Railway restarts it |
| `railway.json` | Dockerfile build, `/healthz` health check, restart on failure, **1 replica** |
| `.dockerignore` | Only the four Rust crates and `deploy/` reach the build |
| `deploy/railway-vars.sh` | Writes all Railway variables into one local file (outside the repo) for the Raw Editor |

## The wallet on Railway

The deployment uses its own testnet wallet, **`prod-treasury`** (birthday
4,525,762), funded with 0.39 TAZ from the local treasury (tx
`a294bebe…e51e`). Never run a local payout service on `prod-treasury`: the
copy on this PC is its backup only.

Its secrets reach Railway as two separate variables; neither alone can spend:

* `WALLET_AGE_IDENTITY`: the age identity (`AGE-SECRET-KEY-1…`).
* `WALLET_MNEMONIC_AGE_B64`: the encrypted seed (`mnemonic.age`, base64).

On every start `deploy/start.sh`:
1. writes the identity to memory (`/dev/shm`), never to the volume;
2. writes the encrypted seed to the volume;
3. refuses to start if the two don't match.

On the **first** start it also creates the wallet database with the existing
`hushush-wallet-proof restore`, the seed decrypted in memory and piped in. The
plaintext seed is never written to disk or logged. The wallet then syncs from
its birthday.

**The volume is essential:**
* it holds the payment-intent store that makes each payout exactly-once;
* never delete it, and never run more than one replica.

## Variables

Generated by `bash deploy/railway-vars.sh` into
`%LOCALAPPDATA%\hushush-dev\railway.env`:

| Variable | Notes |
|---|---|
| `WALLET_NAME`, `WALLET_BIRTHDAY` | `prod-treasury`, 4525762 |
| `WALLET_LIGHTWALLETD_URL` | `https://testnet.zec.rocks:443` (checked to be the NU7 testnet on every start) |
| `WALLET_AGE_IDENTITY`, `WALLET_MNEMONIC_AGE_B64` | **secret**; see above |
| `WALLET_API_TOKEN` | **secret**; payroll-api ↔ wallet, never leaves the container |
| `PAYROLL_API_TOKEN` | **secret**; the same value goes to Vercel |
| `PAYOUT_ADDRESS_KEY` | **secret**; seals workers' locked addresses. **Never change it** after the first sign-up, or stored addresses become unreadable. Kept in `%LOCALAPPDATA%\hushush-dev\railway-payout-address-key.txt` |
| `PAYROLL_DATABASE_URL` | **secret**; Supabase **session pooler** (port 5432), not the transaction pooler |
| `PAYROLL_DATABASE_CA_PEM` | Supabase CA (one line, `\n` escapes accepted); TLS is then mandatory and verified |
| `PAYROLL_DB_POOL_SIZE` | `5` behind the pooler |
| `PAYOUT_ENABLED_ORGS` | `*` (testnet) |
| `PAYOUT_CONFIRMATIONS` | `10` |

Set by the start script (don't set them): `PORT` (Railway sets it),
`PAYROLL_API_ADDR`, `PAYROLL_API_ALLOW_NONLOCAL=1`, `WALLET_URL`,
`HUSHUSH_DATA_DIR=/data/hushush`.

**On `PAYROLL_API_ALLOW_NONLOCAL=1`:** payroll-api is public so that Vercel can
reach it.
* Railway terminates TLS at its edge.
* Every request needs `PAYROLL_API_TOKEN`.
* The wallet stays on loopback.

## Steps

1. **Supabase.** Reset the database (it still holds rehearsal data): SQL
   editor → `drop schema public cascade; create schema public;`.
   payroll-api migrates it on its first start. The web app's migrations run
   from Vercel's side (or once locally with `npm run db:migrate`).
2. **Railway project.** New Project → Deploy from GitHub repo → this repo,
   branch `main`. Railway reads `railway.json` and builds `deploy/api.Dockerfile`.
   The first build takes 20–40 minutes.
3. **Volume.** Service → Settings → Volumes → add one, mount path **`/data`**.
4. **Variables.** Run `bash deploy/railway-vars.sh`, then paste
   `railway.env` into Variables → Raw Editor. Save, then delete the file.
5. **Domain.** Service → Settings → Networking → Generate Domain. This is the
   `PAYROLL_API_URL` for Vercel.
6. **Deploy and check:**
   * the logs show `start: first start … creating its database`, then the
     wallet syncing and `payout wallet listening on 127.0.0.1:7979`;
   * `https://<domain>/healthz` answers.
7. **Funding.** The 0.39 TAZ is already in `prod-treasury`'s main account. The
   dashboard's faucet moves test TAZ from it to each company's own account.

## Limits

* **Testnet only.** This puts a spending key on Railway's servers. That's
  acceptable on testnet and ruled out for mainnet
  ([MAINNET_OPTION_B_SELF_CUSTODY.md](MAINNET_OPTION_B_SELF_CUSTODY.md)).
* **Downtime on redeploys.** A redeploy stops the running container before the
  new one starts: the volume can't be shared, and the wallet lock refuses a
  second instance anyway.
* **Re-syncs.** If the volume is lost, payouts in flight need manual
  reconciliation. The wallet re-syncs from its birthday on the next start.
